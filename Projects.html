Home Lab Build Order

How this page is organized: sections are listed in the order you’d build a home lab, starting with the hypervisor that everything else runs on. Each phase relies on the ones before it, so working top to bottom avoids redoing things later.

  1. Foundation: Hypervisor (Proxmox), Networking, Static IPs, MAC Addresses. Install the host and give every machine a predictable address.
  2. Base server setup: Core Services (SSH, keys, CLI tools, Docker, Tailscale), Security Hardening. The tools almost every server needs, then lock it down.
  3. Network services: DNS, Pi-hole, NTP, Windows Server. Name resolution, ad blocking, time and directory services the rest of the lab uses.
  4. Storage: RAID, NAS, Samba. Redundant disks and shared folders for media and backups.
  5. Reverse proxy and apps: Nginx Proxy Manager, Vaultwarden, Plex, Home Assistant. HTTPS and friendly names first, then the self-hosted apps behind them.
  6. Scale and automate: Kubernetes, Automation, Scripting, Bash, PowerShell.
  7. Monitor and protect: Central Logging, Alerting, Backups, GPG.
  8. Extras and reference: SQL, Deploy an HTML Site, HTML, Troubleshoots, Command Dictionary.

MAC addresses

What it is: A MAC (Media Access Control) address is the unique hardware identifier of a network interface, written as six pairs of hexadecimal characters (for example 3C:52:82:1A:4F:9B). Switches use MAC addresses to deliver traffic on the local network, and routers use them for DHCP reservations and device filtering.

DNS

What it is: DNS (Domain Name System) is the internet’s phone book. People use names like ryanpgray.com; computers connect using IP addresses like 185.199.108.153. DNS translates one into the other, every time you open a website, send an email or connect to a server by name. Records at your DNS provider decide where a domain and each of its subdomains point.

What DNS Is and Why It Exists

▶ Watch this in the tutorial (15:37)

  • IP address: every device on a network (your PC, your phone, a web server) has an IP address, like a phone number for the internet. IPv4 looks like 192.168.1.10; IPv6 looks like 2606:50c0:8000::153 and exists because the world is running out of IPv4 numbers.
  • Domain name: a human-friendly name that is easy to remember and doesn’t change when the server behind it moves to a new address.
  • DNS: a worldwide, distributed database that maps names to addresses (and other information, such as which servers handle email). No single server holds everything; each domain’s records live with that domain’s DNS provider.

Without DNS you would have to type an IP address for every site. With it, a site can move to a new server and only its DNS record changes; everyone keeps using the same name.

How a DNS Lookup Works

When you type www.example.com into a browser, this happens in a fraction of a second:

  1. Local cache: your browser and operating system first check whether they looked the name up recently. If so, they reuse the answer.
  2. Recursive resolver: if not, the computer asks its configured DNS server, usually your router, your ISP, or a public resolver such as 1.1.1.1 (Cloudflare) or 8.8.8.8 (Google). The resolver does the legwork.
  3. Root servers: the resolver asks a root server, “Who handles .com?”
  4. TLD servers: the .com servers answer, “example.com is handled by these nameservers” (the domain’s NS records, set at the registrar).
  5. Authoritative nameserver: the domain’s own DNS provider returns the actual record, for example the A record with the IP address.
  6. Answer and caching: the resolver returns the IP to your computer, and every step caches the answer for the record’s TTL. The browser then connects to that IP and asks the web server for the page.
ℹ
Registrar vs. DNS host: the registrar is where you buy the domain (Namecheap, Cloudflare, GoDaddy…). The DNS host is whoever answers DNS questions for it, set by the domain’s NS records. They’re often the same company, but you can buy a domain at Namecheap and point its nameservers to Cloudflare, as the NGINX / Vaultwarden guide does.

Host / name field

  • @ means the bare (root) domain itself, e.g. example.com. Some providers leave the field blank instead.
  • Anything else is a subdomain in front of the domain: www → www.example.com, studio → studio.example.com. Subdomains let one domain host several separate sites.
  • * is a wildcard that matches any subdomain without its own record, e.g. *.tail.example.com.

TTL and propagation

TTL (time to live) is how many seconds resolvers may cache a record. A short TTL such as 300 (5 minutes) means changes take effect quickly; a long TTL such as 3600 or 86400 means fewer lookups but slower changes. Lower the TTL a day before a planned move, then raise it again afterwards. “Propagation” is simply old cached answers expiring around the world, which is why new records can take anywhere from minutes to 24–48 hours to work everywhere.

How DNS Is Used

  • Websites: A/AAAA and CNAME records point a domain at a web host, such as GitHub Pages (see the worked example below and Deploy an HTML Site).
  • Email: MX records route incoming mail; TXT records hold SPF, DKIM and DMARC so other servers trust mail sent from the domain.
  • Proving ownership: services ask you to add a TXT record (or CNAME) to verify a domain, and Let’s Encrypt can issue certificates through a DNS challenge, as in the wildcard certificate steps.
  • Internal networks: companies run their own DNS (for example on Windows Server) so PCs find file servers, printers and domain controllers by name; Active Directory depends on it.
  • Home lab: a local DNS server such as Pi-hole answers for your devices, can create local names like nas.home, and blocks ads by refusing to resolve ad domains.
  • Load balancing and failover: several A records for one name spread visitors across servers, as GitHub Pages does with its four addresses.

Pi-Hole

What it is: Pi-hole is a network-wide ad blocker that works as your network’s DNS server. Devices ask Pi-hole to look up names like google.com; Pi-hole forwards normal lookups to a real (upstream) DNS server such as 1.1.1.1, but when a device asks for a known ad or tracking domain, Pi-hole answers with nothing (0.0.0.0), so the ad never loads. Because it works at the DNS level, it covers every device on the network (phones, smart TVs, game consoles) without installing anything on them.

What Pi-hole Does

▶ Watch this step (0:35)

  • Network-wide ad and tracker blocking: blocklists (“adlists”) contain hundreds of thousands of ad, tracking and malware domains. Lookups for them are blocked for every device that uses Pi-hole as its DNS server.
  • DNS caching: answers are remembered, so repeat lookups are instant and browsing feels a little faster.
  • Local DNS records: give home-lab machines easy names, e.g. ubuntu-server.home.arpa instead of 192.168.1.93.
  • Query log and dashboard: see which devices look up what, how many queries were blocked, and the top domains.
  • Optional DHCP server: Pi-hole can hand out IP addresses if your router can’t point clients at a custom DNS server.
ℹ
Limits: DNS blocking can’t remove ads served from the same domain as the content (YouTube video ads, many social-media ads) and can’t block apps or devices that use their own hard-coded or encrypted DNS (DNS-over-HTTPS). Pair it with a browser ad blocker for the best results.

Step 6: Use Pi-hole for the Whole Network

▶ Watch this step (7:37)

Your router tells every device which DNS server to use when it hands out IP addresses (DHCP). Change that setting once and every device follows:

⚠
About a backup DNS server: the video suggests adding a public DNS (like 1.1.1.1) as the second DNS server in case Pi-hole goes down. That keeps the internet working, but devices often use the second server even when Pi-hole is fine, so some ads will get through. The cleaner fix is a second Pi-hole as the backup DNS.

Option B: router WAN/Internet DNS. Some routers only let you change their own upstream DNS. Setting it to Pi-hole works, but every query then shows up as coming from the router, so you lose per-device stats.

▶ Watch this step (8:08)

ℹ

Security and Optional Extras

  • Never expose port 53 to the internet. An open DNS resolver gets abused in DDoS attacks. Keep Pi-hole on your LAN, or reach it remotely over a VPN such as Tailscale, which can push Pi-hole as the DNS server for all your devices away from home.
  • Back up your settings: Settings → Teleporter exports and import all lists and records. For Docker, back up the etc-pihole folder.
  • Redundancy: run a second Pi-hole on another device and set it as the secondary DNS, so blocking keeps working if one goes down.
  • Unbound (optional): instead of forwarding to Cloudflare or Google, Pi-hole can use a local Unbound recursive resolver that asks the root servers directly, so no single upstream provider sees all your lookups. See the official “Pi-hole as All-Around DNS Solution” guide.

RAID

What it is: RAID (Redundant Array of Independent Disks) combines several physical drives into one logical drive for more speed, more redundancy, or both. This guide builds a software RAID on Ubuntu Server with mdadm, entirely over SSH. No hardware RAID card is needed.

⚠
Creating an array erases every disk you add to it. Back up anything on those disks first, and double-check the device names before running the create command.
ℹ
RAID is not a backup. It keeps the server running when a disk dies, but it will happily mirror an accidental delete, ransomware, or a corrupted file to every disk. Keep separate backups.

Choosing a RAID Level

LevelMin. disksUsable spaceSurvivesBest for
RAID 0 (stripe)2100% of all disksNo disk failuresScratch space, speed only. Losing one disk loses everything.
RAID 1 (mirror)2Size of one diskAll but one diskBoot/OS data, small home servers. Simple and safe.
RAID 5 (parity)3Total − 1 disk1 diskMedia and file storage with a good balance of space and safety.
RAID 6 (double parity)4Total − 2 disks2 disksLarge arrays of big drives, where rebuilds take a long time.
RAID 10 (mirror + stripe)450% of all disks1 disk per mirror pairVMs and databases that need speed and redundancy.

Use disks of the same size. The array treats every member as the size of the smallest one.

Setting Up a RAID Array over SSH

The examples below use the disks /dev/sdb, /dev/sdc, /dev/sdd and /dev/sde, the array name /dev/md0, and the mount point /mnt/raid. Replace the disk names with your own from Step 3.

Step 1: Connect to the server

From your computer, open a terminal (PowerShell on Windows) and connect:

bash 
ssh username@server-ip
💡
If you lose the SSH connection while the array is building, nothing breaks. The build keeps running on the server. Just reconnect and check progress with cat /proc/mdstat.

Step 2: Update the system and install mdadm

bash 
sudo apt update
sudo apt upgrade -y
sudo apt install mdadm -y

If the installer shows a mail configuration screen (Postfix), choose No configuration unless you already run a mail server.

Step 3: Identify the disks

List every disk with its size and whether it is already in use:

bash 
lsblk -o NAME,SIZE,FSTYPE,TYPE,MOUNTPOINTS

For more detail, including the model of each disk:

bash 
sudo fdisk -l

The new, empty disks usually show no partitions and no mount point. Write down their names (for example sdb, sdc).

⚠
Do not use the disk that holds Ubuntu. It is the one with partitions mounted at / or /boot, usually sda or nvme0n1.

Step 4: Wipe old data from the disks

Remove any old partition tables or filesystem signatures (list every disk you will use):

bash 
sudo wipefs -a /dev/sdb /dev/sdc

If a disk was ever part of another RAID array, also clear its old RAID metadata. An error saying “Unrecognised md component device” just means there was nothing to clear.

bash 
sudo mdadm --zero-superblock /dev/sdb /dev/sdc

Step 5: Create the array

Run only the one command for the RAID level you chose. When asked Continue creating array?, type y and press Enter.

RAID 1 (2 disks):

bash 
sudo mdadm --create --verbose /dev/md0 --level=1 --raid-devices=2 /dev/sdb /dev/sdc

RAID 5 (3 disks):

bash 
sudo mdadm --create --verbose /dev/md0 --level=5 --raid-devices=3 /dev/sdb /dev/sdc /dev/sdd

RAID 6 (4 disks):

bash 
sudo mdadm --create --verbose /dev/md0 --level=6 --raid-devices=4 /dev/sdb /dev/sdc /dev/sdd /dev/sde

RAID 10 (4 disks):

bash 
sudo mdadm --create --verbose /dev/md0 --level=10 --raid-devices=4 /dev/sdb /dev/sdc /dev/sdd /dev/sde

RAID 0 (2 disks, no redundancy):

bash 
sudo mdadm --create --verbose /dev/md0 --level=0 --raid-devices=2 /dev/sdb /dev/sdc

Step 6: Watch the initial sync

RAID 1, 5, 6 and 10 now sync the disks in the background. This can take hours on large drives. Check progress:

bash 
cat /proc/mdstat

Or refresh it every 5 seconds (press Ctrl + C to stop watching):

bash 
watch -n 5 cat /proc/mdstat

You can keep going with the next steps while it syncs. The array is usable right away, just slower until the sync finishes.

Step 7: Create a filesystem

bash 
sudo mkfs.ext4 -F /dev/md0

Step 8: Mount the array

bash 
sudo mkdir -p /mnt/raid
sudo mount /dev/md0 /mnt/raid

Confirm it is mounted and shows the expected size:

bash 
df -h /mnt/raid

Step 9: Make the array survive a reboot

Save the array layout so Ubuntu reassembles it at boot:

bash 
sudo mdadm --detail --scan | sudo tee -a /etc/mdadm/mdadm.conf
sudo update-initramfs -u
⚠
Run the tee -a command above only once. Running it twice adds a duplicate ARRAY line. If that happens, open the file with sudo nano /etc/mdadm/mdadm.conf and delete the extra line.

Add the array to /etc/fstab by its UUID so it mounts automatically. nofail lets the server still boot if the array has a problem:

bash 
echo "UUID=$(sudo blkid -s UUID -o value /dev/md0) /mnt/raid ext4 defaults,nofail 0 2" | sudo tee -a /etc/fstab

Test the fstab entry without rebooting. No output from mount -a means it worked:

bash 
sudo umount /mnt/raid
sudo mount -a
findmnt /mnt/raid

Step 10: Give your user access

The new filesystem is owned by root. Let your own account read and write to it:

bash 
sudo chown -R $USER:$USER /mnt/raid

Step 11: Reboot and verify

bash 
sudo reboot

Wait a minute, reconnect with SSH, then check the array:

bash 
ssh username@server-ip
bash 
cat /proc/mdstat
sudo mdadm --detail /dev/md0
df -h /mnt/raid

In the mdadm --detail output, look for State : clean (or active) and every disk listed as active sync.

Checking Health and Replacing a Failed Disk

Check array health

bash 
cat /proc/mdstat
sudo mdadm --detail /dev/md0

In /proc/mdstat, [UU] means every disk is up. An underscore, such as [U_], means a disk has failed or is missing and the array is running degraded.

Check a single disk’s own health report (install the tools first):

bash 
sudo apt install smartmontools -y
sudo smartctl -H /dev/sdb

Replace a failed disk

1. Find which disk failed (it is marked faulty or removed):

bash 
sudo mdadm --detail /dev/md0

2. Mark the disk as failed and remove it from the array (replace /dev/sdc with the failed disk):

bash 
sudo mdadm /dev/md0 --fail /dev/sdc
sudo mdadm /dev/md0 --remove /dev/sdc

3. Note the failed disk’s serial number so you pull the right physical drive, then shut down and swap it:

bash 
sudo smartctl -i /dev/sdc | grep -i serial
sudo shutdown now

4. After booting back up and reconnecting over SSH, find the new disk’s name with lsblk, then add it to the array (here the new disk is /dev/sdf):

bash 
lsblk -o NAME,SIZE,FSTYPE,TYPE,MOUNTPOINTS
sudo wipefs -a /dev/sdf
sudo mdadm /dev/md0 --add /dev/sdf

5. Watch the rebuild until it reaches 100%:

bash 
watch -n 5 cat /proc/mdstat

Troubleshooting

The array shows up as /dev/md127 after a reboot

The layout was not saved in Step 9. Stop the array, reassemble it under the right name, and save the config:

bash 
sudo umount /mnt/raid
sudo mdadm --stop /dev/md127
sudo mdadm --assemble --scan
sudo mdadm --detail --scan | sudo tee -a /etc/mdadm/mdadm.conf
sudo update-initramfs -u
sudo mount -a

The array is inactive or not mounted after a reboot

bash 
sudo mdadm --assemble --scan
sudo mount -a
cat /proc/mdstat

“Device or resource busy” when creating or stopping the array

Something is still using the disk. Check for mount points, then unmount before trying again:

bash 
lsblk -o NAME,MOUNTPOINTS
sudo umount /dev/sdb1

Deleting an array completely

⚠
This permanently destroys all data on the array.
bash 
sudo umount /mnt/raid

Then remove the /dev/md0 line from /etc/mdadm/mdadm.conf and the /mnt/raid line from /etc/fstab (sudo nano each file), and run sudo update-initramfs -u.

Linux: Two Ways to Connect

Both routes do the same thing in the end: the haven-share folder on the server shows up as a folder on your Linux computer, and you log in with the same username (haven) and the same Samba password. The difference is who types the password, and when.

First, it helps to know the two password pieces involved, because they’re easy to mix up:

PieceWhereWhat it does
sudo smbpasswd -a havenOn the serverSets the password the share will accept. Every route needs this. Like setting the combination on a lock.
~/.smbcredentialsA file on the Linux computerStores a copy of that same password so the computer can log in by itself, with nobody there to type it. Like a note of the combination kept by the door.
ℹ
The Linux computer can’t read the server’s Samba password list, so smbpasswd alone can’t log it in automatically. Something on the client has to supply the password: you (Route A) or the credentials file (Route B). In both cases it must match the password you set with smbpasswd.

Route A: Sign In with Your Samba Password (Recommended)

1. Make sure the Samba password is set. You already did this in Step 3; run it again any time to reset the password:

bash · on the server 
sudo smbpasswd -a haven

2. Connect from the Linux computer. Open Files → Other Locations, type the address below in Connect to Server and click Connect. Choose Registered User, enter username haven and the Samba password, and pick Remember forever so next time it’s one click. Right-click the share in the sidebar and Add Bookmark to keep it handy.

text · type in Connect to Server 
smb://192.168.1.51/haven-share

Prefer the terminal? This mounts the share at /mnt/haven-share and asks for the Samba password (nothing shows while you type). It stays connected until you restart the computer:

bash · on the Linux computer 
sudo apt install -y cifs-utils
sudo mkdir -p /mnt/haven-share
sudo mount -t cifs //192.168.1.51/haven-share /mnt/haven-share -o username=haven,uid=$(id -u),gid=$(id -g)

To disconnect: sudo umount /mnt/haven-share.

Route B: Auto-Mount at Boot with fstab

Use this on a Linux computer (not the server) that should always have the share at /mnt/haven-share, even before anyone signs in. On Windows, ticking Reconnect at sign-in in Map network drive is the equivalent. The example assumes your username on that computer is also haven, and that the Samba password is already set on the server with sudo smbpasswd -a haven.

1. Install the tools for mounting Windows/Samba shares:

bash · on the Linux computer 
sudo apt install -y cifs-utils

2. Create the folder the share will appear in (the “mount point”):

bash · on the Linux computer 
sudo mkdir -p /mnt/haven-share

3. Save a copy of the Samba password on this computer in ~/.smbcredentials. This is the “note by the door”: the same password you set with smbpasswd, kept here so the computer can log in at startup. Pick either way:

Option 1 (easiest): one command. It asks for the password and hides it as you type, then writes the file and makes it readable only by you:

bash · on the Linux computer 
read -rsp "Samba password for haven: " SMBPASS; echo
printf 'username=haven\npassword=%s\n' "$SMBPASS" > ~/.smbcredentials
unset SMBPASS
chmod 600 ~/.smbcredentials

Option 2: write it in a text editor. Open a new file:

bash · on the Linux computer 
nano ~/.smbcredentials

Paste these two lines, replacing the password with your Samba password, then save with Ctrl+X, Y, Enter:

text · contents of ~/.smbcredentials 
username=haven
password=YourSambaPassword

Make the file readable only by you:

bash · on the Linux computer 
chmod 600 ~/.smbcredentials

Either way, check it with cat ~/.smbcredentials. If you ever change the password with smbpasswd on the server, update this file too.

4. Find your user and group ID numbers (so the files show up as yours). On most single-user systems both are 1000:

bash · on the Linux computer 
id -u
id -g

5. Add the share to /etc/fstab, the file Linux reads at startup to know what to mount:

bash · on the Linux computer 
sudo nano /etc/fstab

Go to the bottom of the file and paste this as one line. If step 4 showed numbers other than 1000, change them. Save and exit:

text · add to the end of /etc/fstab 
//192.168.1.51/haven-share  /mnt/haven-share  cifs  credentials=/home/haven/.smbcredentials,uid=1000,gid=1000,_netdev,nofail  0  0
Part of the lineMeaning
//192.168.1.51/haven-shareThe share to connect to: the server’s IP and share name.
/mnt/haven-shareThe folder on this computer where the share appears (from step 2).
cifsThe type of share (Windows/Samba file sharing).
credentials=/home/haven/.smbcredentialsWhere to read the username and password (from step 3).
uid=1000,gid=1000Make the files owned by your user and group (from step 4), so you can edit them.
_netdevWait until the network is up before mounting.
nofailIf the server is off, keep booting normally instead of stopping with an error.
0 0Skip the old “dump” backup and the startup disk check (always 0 0 for network shares).

6. Test it without rebooting. mount -a mounts everything in /etc/fstab; if it prints no errors and ls shows your files, it will also work at boot:

bash · on the Linux computer 
sudo systemctl daemon-reload
sudo mount -a
ls /mnt/haven-share
⚠
A typo in /etc/fstab can cause boot problems, which is why the line uses nofail and why you test with sudo mount -a first. If something goes wrong, open the file again and delete or fix the line. Error 13 (permission denied) means the username or password in ~/.smbcredentials is wrong.

Storage, Protection and Next Steps

  • One drive means no redundancy. The video stores everything on a single 2 TB disk; if it fails, the data is gone. Add a second drive and mirror them with RAID 1, or use a NAS OS that handles redundancy for you.
  • RAID is not a backup. Follow the 3-2-1 rule: 3 copies of important data, on 2 different types of storage, with 1 copy off-site (see Backups).
  • Folder layout: keep media in one place, e.g. ~/haven-share/plex/movies and ~/haven-share/plex/shows, so Plex and the share use the same folders.
  • Keep it on the LAN: don’t forward Samba (port 445) through your router. For access away from home, use a VPN such as Tailscale.
  • Check disk health now and then: sudo apt install smartmontools, then sudo smartctl -H /dev/sda.
  • Dedicated NAS systems: if you’d rather click than type, TrueNAS, OpenMediaVault and Unraid are operating systems built just for NAS boxes, with web dashboards, RAID and app support.

Step 3: Back Up Your Key and Revocation Certificate

Do this right after creating the key. If you lose your private key you can’t decrypt anything sent to you, and without a revocation certificate you can’t tell people to stop using it.

GnuPG 2.1+ creates a revocation certificate automatically in ~/.gnupg/openpgp-revocs.d/. To make one yourself:

bash · terminal 
gpg --output haven-revoke.asc --gen-revoke haven@example.com

Export a backup of your private key (it stays protected by your passphrase):

bash · terminal 
gpg --armor --export-secret-keys haven@example.com > haven-private-key.asc
⚠
Store both files offline: an encrypted USB drive, or printed and kept somewhere safe. Never email them, put them in cloud storage unencrypted, or commit them to Git. Anyone with the revocation file can revoke your key.

Restore the backup on a new computer:

bash · terminal 
gpg --import haven-private-key.asc
gpg --edit-key haven@example.com   # then type: trust, 5 (ultimate), y, save

Keep the keyring folder private (GPG warns about “unsafe permissions” otherwise):

bash · terminal 
chmod 700 ~/.gnupg
chmod 600 ~/.gnupg/*

Step 5: Encrypt and Decrypt Files (Linux and Windows)

There are two ways to encrypt a file. Pick one based on who needs to open it:

MethodUse it whenWho can decrypt
Public-key (--encrypt)Sending a file to a specific person, or encrypting for yourself with your keyOnly the holders of the recipients’ private keys
Password (--symmetric)Backups, or sharing with someone who doesn’t use GPGAnyone who knows the passphrase
ℹ
A file encrypted on Linux decrypts on Windows and the other way round. The commands are the same on both; only the file paths and the graphical tools differ. To encrypt for someone, you need their public key imported first (see Step 4).

Linux: Encrypt a File for Someone

  1. Check that the recipient’s key is in your keyring:
bash · Linux terminal 
gpg --list-keys alice@example.com
  1. Encrypt the file. Add yourself as a second recipient so you can still open your own copy:
bash · Linux terminal 
gpg --encrypt --recipient alice@example.com --recipient haven@example.com --output report.pdf.gpg report.pdf
  1. Confirm the encrypted file exists, then send report.pdf.gpg. Optionally destroy the unencrypted original:
bash · Linux terminal 
ls -l report.pdf.gpg
shred -u report.pdf    # optional: overwrite and delete the original
💡
Need text you can paste into an email or chat instead of a binary file? Add --armor and name the output .asc: gpg --armor --encrypt --recipient alice@example.com --output notes.txt.asc notes.txt

Linux: Decrypt a File

Run this on the computer that holds your private key. GPG detects which key the file was encrypted to and prompts for that key’s passphrase:

bash · Linux terminal 
gpg --output report.pdf --decrypt report.pdf.gpg

It also prints who the file was encrypted to (and, if it was signed, a Good signature line). On a server over SSH where no passphrase box appears, enter it in the terminal instead:

bash · Linux terminal 
export GPG_TTY=$(tty)
gpg --pinentry-mode loopback --output report.pdf --decrypt report.pdf.gpg

Linux: Encrypt and Decrypt with a Password

bash · Linux terminal 
# encrypt (asks for a new passphrase twice) -> secrets.txt.gpg
gpg --symmetric --cipher-algo AES256 secrets.txt

# decrypt
gpg --output secrets.txt --decrypt secrets.txt.gpg
⚠

# decrypt and unpack into the current folder
gpg --decrypt taxes.tar.gz.gpg | tar xzf -

Windows: Encrypt and Decrypt with Kleopatra (No Commands)

Install Gpg4win (Step 1). It adds Kleopatra and right-click menu entries in File Explorer.

Encrypt:

  1. In File Explorer, right-click the file. On Windows 11, click Show more options first.
  2. Choose More GpgEX options → Sign and encrypt. (Or open Kleopatra and click Sign/Encrypt…, then pick the file.)
  3. For a person: tick Encrypt for others and choose their key. Leave Encrypt for me ticked so you can open it too. For a password instead: tick Encrypt with password and untick the others.
  4. Untick Sign as if you only want encryption, check the output file name (it ends in .gpg), then click Encrypt.
  5. Kleopatra shows “Encryption succeeded”. Send or store the .gpg file.

Decrypt:

  1. Right-click the .gpg file → More GpgEX options → Decrypt and verify. (Or double-click it, or use Kleopatra’s Decrypt/Verify… button.)
  2. Enter the passphrase for your key (or the file’s password) when asked.
  3. Click Save All. The original file appears next to the encrypted one.

Windows: Encrypt and Decrypt in PowerShell

Gpg4win also installs the gpg command. Open a new PowerShell window after installing and check it works with gpg --version. Then cd to the folder with the file:

powershell · Windows 
cd "$env:USERPROFILE\Documents"

Encrypt for someone (plus yourself):

powershell · Windows 
gpg --encrypt --recipient alice@example.com --recipient haven@example.com --output report.pdf.gpg report.pdf

Decrypt (a passphrase window appears):

powershell · Windows 
gpg --output report.pdf --decrypt report.pdf.gpg

Password-only encryption and decryption:

powershell · Windows 
gpg --symmetric --cipher-algo AES256 secrets.txt
gpg --output secrets.txt --decrypt secrets.txt.gpg

A whole folder: zip it, encrypt the zip, then delete the unencrypted zip. To restore, decrypt and unzip:

powershell · Windows 
# encrypt
Compress-Archive -Path .\Taxes -DestinationPath Taxes.zip
gpg --symmetric --cipher-algo AES256 --output Taxes.zip.gpg Taxes.zip
Remove-Item Taxes.zip

# decrypt and unzip
gpg --output Taxes.zip --decrypt Taxes.zip.gpg
Expand-Archive -Path Taxes.zip -DestinationPath .\Taxes-restored
💡
Use quotes around paths with spaces, e.g. gpg --output "My Report.pdf" --decrypt "My Report.pdf.gpg". Always put --output before --decrypt. In PowerShell, don’t redirect decrypted output with >; Windows PowerShell 5.1 re-encodes it and corrupts binary files like PDFs and zips.

Encrypt and Sign Together

Adding --sign proves the file came from you. The recipient sees Good signature from "Haven Example" when they decrypt. This works the same on Linux and in PowerShell; in Kleopatra, leave Sign as ticked.

bash · Linux or PowerShell 
gpg --sign --encrypt --recipient alice@example.com --recipient haven@example.com --output contract.pdf.gpg contract.pdf

Real-World Example: Verify a Downloaded ISO

Before installing an OS like Ubuntu, Debian or Proxmox, confirm the ISO is genuine. Projects publish a checksum file and a GPG signature of that file. Using Ubuntu as the example:

  1. Download the ISO plus SHA256SUMS and SHA256SUMS.gpg from the same release folder.
  2. Check the signature on the checksum file. The first time, it fails with “No public key” and shows the key ID it needs:
bash · terminal 
gpg --keyid-format long --verify SHA256SUMS.gpg SHA256SUMS
  1. Fetch that key from the project’s keyserver and compare its fingerprint with the one on the project’s official website:
bash · terminal 
gpg --keyserver hkps://keyserver.ubuntu.com --recv-keys <KEY-ID-FROM-THE-MESSAGE>
gpg --fingerprint <KEY-ID-FROM-THE-MESSAGE>
gpg --keyid-format long --verify SHA256SUMS.gpg SHA256SUMS   # now: Good signature
  1. Check the ISO against the now-trusted checksum list:
bash · terminal 
sha256sum -c SHA256SUMS --ignore-missing
# ubuntu-24.04-live-server-amd64.iso: OK
ℹ
On Windows, check the hash with Get-FileHash .\ubuntu.iso -Algorithm SHA256 in PowerShell and compare it with the line in SHA256SUMS. Kleopatra can verify the .gpg signature.

Real-World Example: Sign Git Commits (GitHub “Verified”)

  1. Find your key ID: gpg --list-secret-keys --keyid-format=long (the part after ed25519/).
  2. Tell Git to use it and sign every commit:
bash · terminal 
git config --global user.signingkey 3AA5C34371567BD2
git config --global commit.gpgsign true
git config --global tag.gpgsign true
  1. Add your public key to GitHub: copy the output of the command below into Settings → SSH and GPG keys → New GPG key.
bash · terminal 
gpg --armor --export 3AA5C34371567BD2
  1. Commit as usual. GitHub shows a Verified badge when the key’s email matches a verified email on your account. Check locally with git log --show-signature -1.
⚠
If commits fail with gpg: signing failed: Inappropriate ioctl for device, add export GPG_TTY=$(tty) to ~/.bashrc (or ~/.zshrc) and open a new terminal.

Managing Keys: Expiry, Editing, Revoking

Extend the expiry before it runs out (do the primary key and all subkeys), then re-share your public key:

bash · terminal 
gpg --quick-set-expire A1B2C3D4E5F6A7B8C9D0E1F23AA5C34371567BD2 2y
gpg --quick-set-expire A1B2C3D4E5F6A7B8C9D0E1F23AA5C34371567BD2 2y '*'

Interactive editing with gpg --edit-key haven@example.com, then:

CommandDoes

Revoke a key that’s lost or compromised: import the revocation certificate, then publish the revoked key so others see it:

bash · terminal 
gpg --import haven-revoke.asc
gpg --keyserver hkps://keys.openpgp.org --send-keys A1B2C3D4E5F6A7B8C9D0E1F23AA5C34371567BD2

Delete a key from your keyring (secret part first):

bash · terminal 
gpg --delete-secret-keys alice@example.com
gpg --delete-keys alice@example.com

Passphrase caching: gpg-agent remembers your passphrase for a while. Clear it immediately with:

bash · terminal 
gpgconf --kill gpg-agent

To change how long it remembers (seconds), add to ~/.gnupg/gpg-agent.conf, then restart the agent:

ini · ~/.gnupg/gpg-agent.conf 
default-cache-ttl 600
max-cache-ttl 7200

Best Practices

  • Protect the private key: strong passphrase, offline backup, never share or upload it.
  • Set an expiry (1–2 years) and extend it on schedule; put a calendar reminder a month before.
  • Create the revocation certificate now, not when you need it.
  • Verify fingerprints through a second channel before trusting a key; never trust a key just because a keyserver returned it.
  • Use modern algorithms: Ed25519/Cv25519, or RSA 4096 if compatibility requires it.
  • Encrypt to yourself too (add your own --recipient) so you can read what you sent.
  • Advanced: keep the primary key offline and use subkeys day-to-day, or store keys on a hardware token such as a YubiKey.

Deploy an HTML Site

What it is: Deploying an HTML site means putting your pages on a web server that is always online, so anyone can open them in a browser. This guide uses GitHub Pages, a free service that publishes static sites (HTML, CSS, JavaScript and images) straight from a GitHub repository, then connects a custom domain such as yourname.com using DNS records and turns on free HTTPS.

These steps follow the video tutorial below (SuperSimpleDev). Each step links to the matching point in the video.

Video Tutorial: https://youtu.be/p1QU3kLFPdg

Before You Start

  • A website made of HTML and CSS files on your computer. No website yet? Download the video’s sample site: open it on GitHub, click Code → Download ZIP, and unzip it.
  • A free GitHub account.
  • For Part 2 only: about $10–15 a year for a domain name.

Useful links:

  • Namecheap: domain registrar used in the video
  • MxToolbox DNS Lookup: shows which IP addresses a domain points to
  • GitHub Docs: Managing a custom domain: GitHub’s own IP addresses and instructions for other registrars

Part 1: Put the Website on the Internet (GitHub Pages)

Opening an HTML file on your own computer only works for you. GitHub Pages copies your files to GitHub’s web servers so anyone can reach them.

▶ Watch this step (2:08)

Step 1: Sign in to GitHub

Go to github.com and sign in, or sign up for a new account and then sign in.

Step 2: Create a public repository

A repository is like a folder on GitHub that holds your website’s files.

  1. Click your profile icon (top right) → Your repositories → New.
  2. Repository name: anything that helps you recognize it, for example super-simple-website.
  3. Select Public. GitHub Pages is only free for public repositories.
  4. Leave the other options at their defaults and click Create repository.

Step 3: Upload your website’s files

▶ Watch this step (3:34)

  1. In the new repository, click uploading an existing file. If you don’t see the link, add /upload to the end of the repository’s URL.
  2. On your computer, open your website’s folder, select everything inside it, and drag the files into the upload box.
  3. Wait for every file to finish uploading, scroll to the bottom and click Commit changes.
⚠
Drag the files inside your folder, not the folder itself. Dragging the folder adds an extra folder level in the repository, and your pages end up at the wrong address.

Step 4: Turn on GitHub Pages

▶ Watch this step (4:50)

  1. In the repository, click Settings (top tab) → Pages (left menu).
  2. Under Build and deployment, set the branch drop-down to main (it may say master; pick whichever isn’t None). Leave the folder as / (root).
  3. Click Save.
  4. Wait a couple of minutes, then refresh the page. It will say Your site is live at followed by the address.

Your site’s default address always follows this pattern:

url 
https://YOUR-USERNAME.github.io/REPOSITORY-NAME/

Step 5: Open your site

▶ Watch this step (5:57)

Open the address in a new tab. If you see a 404 page, that’s normal at this point: add the name of one of your HTML files to the end of the address, for example …/REPOSITORY-NAME/youtube.html, and your page loads. The next step fixes the 404.

Step 6: Add an index.html so the home page loads

▶ Watch this step (8:23)

When an address doesn’t name a file, the web server looks for index.html. No index.html means a 404. Make your main page the home page by renaming it:

  1. In the repository, click your main HTML file (e.g. youtube.html) and click the pencil (Edit this file).
  2. Change the file name at the top to index.html.
  3. Click Commit changes, wait a minute or two, and refresh your site’s address. The home page now loads without a file name.
ℹ
How it works: the repository behaves exactly like the folder on your computer. If your HTML loads styles/general.css locally, it loads the same file from the repository, and images and other files work the same way. So the workflow is simply: build the site on your computer, upload the files, and GitHub Pages publishes them. Every new commit republishes the site within a few minutes.

How the Browser Finds Your Site

▶ Watch this step (15:37)

Before linking the domain, it helps to know what’s happening behind the scenes:

  • Web server: software that hands out files when a browser asks for them. Ask for /index.html and it returns that file; the browser displays HTML as a page. (VS Code’s Live Server is a small web server on your own computer.)
  • Host: the computer the web server runs on. GitHub hosts the servers for GitHub Pages.
  • IP address: like a phone number for every device on the internet. IPv4 looks like 185.199.108.153; IPv6 is longer and exists because IPv4 numbers are running out.
  • DNS record: the link between a domain name and an address, set at your registrar. Once it points your domain at GitHub, typing your domain makes the browser contact GitHub’s servers. See also DNS.

Part 3: Point the Domain at GitHub Pages (DNS Records)

For a deeper explanation of DNS, record types and lookup tools, see the DNS section.

Step 1: Open your domain’s DNS settings

▶ Watch this step (18:51)

In Namecheap: Account → sign in → Domain List → Manage next to your domain → Advanced DNS. Scroll to the Host Records table.

ℹ
Using a different registrar? Look for its DNS records or Manage DNS page (search “manage DNS records” plus your registrar’s name). Every registrar asks for the same four values: Type, Host, Value and TTL.

Step 2: Understand the four values

  • Type: what the record links to. An A record links a name to an IPv4 address; a CNAME record links a name to another domain name.
  • Host: the subdomain, the part before your domain (like studio in studio.youtube.com). Use @ on Namecheap for the bare domain with no subdomain; some registrars leave it blank.
  • Value: the IP address or domain the record points to.
  • TTL (time to live): how quickly changes spread across the internet. Choose 5 min, or enter 300 (seconds) if there’s no drop-down.

Part 4: Connect the Domain in GitHub Pages

▶ Watch this step (26:06)

  1. Go back to your repository on GitHub → Settings → Pages.
  2. Under Custom domain, type your domain (e.g. yourname.com) and click Save. GitHub runs a DNS check.
  3. Open your domain in a new tab. It now shows your site, though the browser may say Not secure until the next part.
⏳

The first should return the four 185.199.x.153 addresses; the second should show it’s an alias of YOUR-USERNAME.github.io.

Part 5: Turn On HTTPS (Free)

▶ Watch this step (27:32)

HTTPS encrypts everything sent between the browser and your site, so no one can read it in transit, and removes the “Not secure” warning.

  1. In Settings → Pages, find Enforce HTTPS.
  2. If the box is greyed out, GitHub is still issuing your certificate. Wait a few minutes and refresh.
  3. Once it’s clickable, check Enforce HTTPS.
  4. Visit https://yourname.com. A lock icon in the address bar means HTTPS is working.
